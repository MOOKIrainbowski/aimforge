# 백엔드 설정 (한국어 상세판)

영어판은 [`README.md`](./README.md)입니다. 이 문서는 같은 절차를 화면 단위로
더 자세히 풀어쓴 것으로, Supabase나 Google OAuth를 처음 다루는 경우를
기준으로 썼습니다.

**먼저 알아둘 것**: AimonSite는 백엔드가 없어도 완전히 동작합니다. 건의함은
브라우저의 localStorage에 저장되고, 로그인 버튼은 아예 표시되지 않으며,
네트워크 요청도 하지 않습니다. 아래 작업은 그 상태를 **계정이 있는 공용
게시판**으로 바꾸는 과정입니다. 한 번만 하면 되고, 빌드 단계나 서버는
필요 없으며, 저장소에 비밀 값을 넣지도 않습니다.

소요 시간은 대략 15~20분이고, 준비물은 Google 계정 하나뿐입니다.

---

## 0. 전체 그림 먼저

작업이 여러 화면을 오가기 때문에, 무엇을 향해 가는지 먼저 봐두면 헤매지
않습니다. 최종적으로 만드는 연결은 이렇습니다.

```
브라우저(AimonSite)
   │  ① "Google로 로그인" 클릭
   ▼
Supabase /auth/v1/authorize
   │  ② Google 로그인 화면으로 넘김
   ▼
Google 계정 선택
   │  ③ 승인되면 Supabase의 callback 주소로 되돌아옴
   ▼
Supabase /auth/v1/callback
   │  ④ 우리가 등록해 둔 Redirect URL로 코드를 붙여 되돌려보냄
   ▼
브라우저(AimonSite)
   │  ⑤ 코드를 토큰으로 교환 → 로그인 완료
   ▼
Supabase REST (posts / comments / profiles)
      ⑥ 이후 모든 읽기·쓰기는 이 토큰으로, RLS 정책의 검사를 받음
```

여기서 **세 곳에 주소를 등록**하게 됩니다. 대부분의 설정 실패는 이 셋 중
하나가 빠져서 생기므로, 나중에 오류가 나면 이 그림으로 돌아오세요.

- Google 쪽에 등록: **③의 주소** (Supabase의 callback)
- Supabase 쪽에 등록: **④의 주소** (AimonSite가 서비스되는 주소)
- 코드에 기록: **Supabase 프로젝트 주소와 anon 키** (⑥에서 쓰는 값)

---

## 1. Supabase 프로젝트 만들기

1. <https://supabase.com> 에 접속해 GitHub 또는 이메일로 가입/로그인합니다.
2. **New project**를 누릅니다.
   - **Name**: 아무 이름이나 괜찮습니다 (예: `aimonsite`).
   - **Database Password**: 강한 비밀번호를 넣고 **어딘가에 저장해 두세요.**
     이 비밀번호는 SQL 편집기 사용에는 필요 없지만, 나중에 DB에 직접
     접속할 때 필요하고 분실하면 재설정해야 합니다.
   - **Region**: 실제 사용자와 가까운 곳을 고릅니다. 한국에서 쓴다면
     `Northeast Asia (Seoul)` 또는 `(Tokyo)`가 응답이 빠릅니다.
   - **Pricing plan**: Free로 충분합니다.
3. 생성에는 1~2분 걸립니다. 프로비저닝이 끝날 때까지 기다립니다.

> **왜 이 단계가 필요한가**: 이 프로젝트 하나가 곧 데이터베이스이자 인증
> 서버이자 REST API입니다. AimonSite가 이야기하는 상대는 처음부터 끝까지
> 이 프로젝트 하나뿐입니다.

## 2. 데이터베이스 스키마 만들기

1. 왼쪽 사이드바에서 **SQL Editor**를 엽니다.
2. **New query**를 누릅니다.
3. 저장소의 [`schema.sql`](./schema.sql) 파일 **전체**를 복사해 붙여넣습니다.
   일부만 실행하면 테이블은 생기고 정책은 안 생기는 어중간한 상태가 되니,
   반드시 전체를 넣으세요.
4. **Run** (또는 Ctrl+Enter)을 누릅니다.
5. 하단에 `Success. No rows returned`가 나오면 정상입니다.

### 이 SQL이 실제로 만드는 것

| 대상 | 역할 |
| --- | --- |
| `profiles` | 계정 1개당 1행. 표시 이름과 `is_admin` 플래그를 보관합니다. |
| `posts` | 건의/오류 제보 글. |
| `comments` | 댓글. `by_admin` 컬럼이 관리자 답변 여부를 나타냅니다. |
| `post_reads` | "누가 이 글을 언제 마지막으로 열어봤는지". 읽지 않은 답변 표시(빨간 점)의 근거입니다. |
| `is_admin()` 함수 | 정책들이 "지금 요청한 사람이 관리자인가"를 물어보는 창구. |
| `on_auth_user_created` 트리거 | 계정이 생기는 즉시 `profiles` 행을 만들어 줍니다. |
| RLS 정책들 | **이 파일에서 가장 중요한 부분.** 아래에서 따로 설명합니다. |

### RLS 정책이 왜 핵심인가

AimonSite는 정적 파일로 배포됩니다. 즉 클라이언트 코드는 전부 사용자
손안에 있고, 개발자 도구를 열면 무엇이든 고쳐 보낼 수 있습니다. 그래서
**클라이언트가 판단하도록 맡긴 것은 전부 거짓말이 가능하다**고 봐야
합니다. 그 대신 다음 세 가지를 서버(PostgreSQL)가 `auth.uid()`를 기준으로
직접 판정합니다.

- **작성자**: 글의 `author_id`는 로그인한 본인이어야만 INSERT가 통과합니다.
  남의 이름으로 글을 쓸 수 없습니다.
- **관리자 답변**: `by_admin = true`인 댓글은 실제로 관리자인 계정만 넣을 수
  있습니다. 이 한 줄이 없으면 "관리자" 배지는 콘솔에서 누구나 켤 수 있는
  체크박스가 됩니다.
- **삭제와 상태 변경**: 관리자만 가능합니다.

여기에 더해, 스키마에는 정책이 아니라 **컬럼 권한**으로 막아둔 것이 하나
있습니다.

```sql
revoke update on public.profiles from authenticated;
grant update (display_name) on public.profiles to authenticated;
```

정책(policy)은 "어떤 **행**을 건드릴 수 있는가"만 정할 수 있고 "어떤
**컬럼**을 건드릴 수 있는가"는 정하지 못합니다. 자기 프로필 행은 수정할 수
있어야 하는데(표시 이름 변경), 같은 행에 `is_admin`도 들어 있습니다. 그래서
컬럼 단위 권한으로 `display_name`만 열어두는 것이고, 이것이 **스스로를
관리자로 승격하는 것을 실제로 막는 장치**입니다. 6단계의 검증은 바로 이
줄이 제대로 적용됐는지를 확인합니다.

## 3. Google 로그인 준비 (Google Cloud 콘솔)

이 단계가 가장 길고, 실패도 대부분 여기서 납니다. 순서대로 하세요.

### 3-1. Supabase의 callback 주소부터 확인

먼저 Supabase 대시보드에서 **Authentication → Providers → Google**을 엽니다.
그 화면 안에 아래와 같은 형태의 **Callback URL (for OAuth)** 이 표시되어
있습니다.

```
https://<프로젝트-ref>.supabase.co/auth/v1/callback
```

이 주소를 복사해 둡니다. 앞의 그림에서 **③에 해당하는 주소**이고, 잠시 뒤
Google에 등록할 값입니다.

> 흔한 오해: 여기에 AimonSite 주소를 넣으면 안 됩니다. Google이 되돌려
> 보내는 곳은 우리 사이트가 아니라 **Supabase**입니다.

### 3-2. OAuth 동의 화면(consent screen) 설정

<https://console.cloud.google.com> 에 접속합니다.

1. 상단에서 프로젝트를 새로 만들거나 기존 것을 선택합니다.
2. **API 및 서비스 → OAuth 동의 화면**으로 들어갑니다.
3. **User Type**은 개인 Google 계정이라면 **외부(External)** 를 선택합니다.
4. 앱 정보를 채웁니다.
   - **앱 이름**: 로그인 화면에 그대로 표시됩니다 (예: `AimonSite`).
   - **사용자 지원 이메일**, **개발자 연락처 이메일**: 본인 이메일.
5. **범위(Scopes)** 는 기본값 그대로 두면 됩니다. 별도로 추가할 필요가
   없습니다 — 이메일과 프로필은 기본 범위에 포함됩니다.
6. **테스트 사용자(Test users)**: 앱이 "테스트 중" 상태인 동안에는 **여기
   등록된 계정만 로그인할 수 있습니다.** 본인 계정을 반드시 추가하세요.
   다른 사람도 쓰게 하려면 나중에 **게시(Publish app)** 를 눌러 프로덕션
   상태로 전환해야 합니다.

> 이 항목을 빠뜨리면 로그인 시도 시 "이 앱은 차단되었습니다" 또는 접근 거부
> 화면이 뜹니다. 코드 문제가 아니라 동의 화면 상태 문제입니다.

### 3-3. OAuth 클라이언트 ID 만들기

1. **API 및 서비스 → 사용자 인증 정보(Credentials)** 로 이동합니다.
2. **사용자 인증 정보 만들기 → OAuth 클라이언트 ID**를 선택합니다.
3. **애플리케이션 유형**: **웹 애플리케이션**을 선택합니다.
4. **승인된 리디렉션 URI**에 3-1에서 복사한 주소를 그대로 붙여넣습니다.

   ```
   https://<프로젝트-ref>.supabase.co/auth/v1/callback
   ```

   - 끝의 `/auth/v1/callback`까지 정확히 포함해야 합니다.
   - 마지막에 슬래시(`/`)를 덧붙이지 마세요. 문자 하나만 달라도
     `redirect_uri_mismatch` 오류가 납니다.
   - "승인된 JavaScript 원본"은 이 방식에서는 채우지 않아도 됩니다.
5. 만들기를 누르면 **클라이언트 ID**와 **클라이언트 보안 비밀번호**가
   나옵니다. 창을 닫지 말고 다음 단계로 갑니다.

### 3-4. Supabase에 붙여넣기

Supabase의 **Authentication → Providers → Google** 화면으로 돌아와서:

1. **Enable Sign in with Google**을 켭니다.
2. **Client ID**와 **Client Secret**에 방금 값을 붙여넣습니다.
3. **Save**.

> 클라이언트 보안 비밀번호는 **Supabase 대시보드에만** 넣습니다. 저장소나
> `config.js`에는 절대 넣지 않습니다. 이 값은 서버 측 비밀입니다.

## 4. 돌아올 주소 등록하기 (Redirect URLs)

Supabase에서 **Authentication → URL Configuration**을 엽니다.

- **Site URL**: 서비스의 기본 주소. 배포된 사이트 주소를 넣습니다
  (예: `https://aimforge.vercel.app`).
- **Redirect URLs**: 로그인 후 되돌아올 수 있는 주소들의 허용 목록입니다.
  여기에 없는 주소로는 절대 되돌려보내지 않습니다. 다음을 추가하세요.

  ```
  https://<배포-주소>/app/index.html
  http://localhost:8123/app/index.html
  ```

  두 번째 줄은 로컬에서 `npm run serve`로 띄웠을 때(포트 8123) 로그인을
  테스트하기 위한 것입니다. 로컬 테스트가 필요 없다면 생략해도 됩니다.

> **왜 이게 따로 필요한가**: Google에 등록한 주소는 "Google → Supabase"
> 구간이고, 여기 등록하는 주소는 "Supabase → AimonSite" 구간입니다. 서로
> 다른 구간이라 양쪽 모두 등록해야 합니다. 이 목록에 빠뜨리면 로그인은
> 성공하는데 사이트로 돌아오지 못하고 멈춘 것처럼 보입니다.

## 5. 앱이 프로젝트를 바라보게 하기

Supabase에서 **Project Settings → API**를 엽니다. 값 두 개가 필요합니다.

- **Project URL** — `https://<프로젝트-ref>.supabase.co`
- **anon public 키** — 대시보드 버전에 따라 `publishable`로 표기되기도
  합니다. 아주 긴 문자열입니다.

이 둘을 [`core/backend/config.js`](../core/backend/config.js)에 넣습니다.

```js
export const SUPABASE_URL = "https://<프로젝트-ref>.supabase.co";
export const SUPABASE_ANON_KEY = "<anon public 키>";
```

저장하고 페이지를 새로고침하면 사이드바에 **Google로 로그인** 버튼이
나타납니다. 두 값이 비어 있는 동안에는 버튼 자체가 표시되지 않으므로,
버튼이 보이면 설정이 인식된 것입니다.

### 이 키를 공개해도 괜찮은 이유

anon 키는 **원래 클라이언트에 담기도록 설계된 값**입니다. 이 키는
"프로젝트가 어디인지"를 알려줄 뿐 "누구인지"를 증명하지 않습니다. 이 키만
가지고 접근하면 RLS 정책상 `authenticated` 역할이 아니므로 사실상 아무것도
읽거나 쓸 수 없습니다. 실제 권한은 로그인 후 발급되는 사용자 토큰(JWT)에서
나오고, 그 판정은 전부 서버에서 이루어집니다.

> ⚠️ **`service_role` 키는 절대 넣지 마세요.** 같은 API 화면에 나란히
> 있지만, 이 키는 **RLS를 통째로 우회합니다.** `config.js`는 모든 방문자에게
> 그대로 전송되는 파일이므로, 이 키를 넣는 순간 데이터베이스 전체가
> 공개됩니다. 실수로 커밋했다면 즉시 대시보드에서 키를 회전(rotate)시키고,
> 커밋 이력에서도 제거해야 합니다.

## 6. 본인을 관리자로 만들기

1. 먼저 앱에서 **한 번 로그인**합니다. 그래야 `auth.users`와 `profiles`에
   계정 행이 생깁니다.
2. Supabase **SQL Editor**에서 본인 이메일로 아래를 실행합니다.

```sql
update public.profiles set is_admin = true
where id = (select id from auth.users where email = 'you@example.com');
```

3. 앱을 새로고침하면 사이드바에 **Admin** 항목이 나타납니다.

관리자 승격을 SQL로만 할 수 있게 한 것은 의도적입니다. "첫 사용자를 자동으로
관리자로" 같은 장치도, 클라이언트에서 도달할 수 있는 경로도 없습니다.
관리자 여부는 데이터베이스의 사실이고, 앱은 그것을 읽기만 합니다.

### 반드시 한 번은 직접 확인해야 하는 것

모의 테스트가 답해줄 수 없는 것이 딱 하나 있습니다. **스키마의 컬럼 권한이
당신의 프로젝트에 실제로 적용됐는가.** 로그인한 상태에서 브라우저 콘솔을
열고 다음을 실행하세요.

```js
const { rest } = await import("/core/backend/supabaseClient.js");
await rest("/profiles?id=eq.<본인-user-id>", {
  method: "PATCH",
  body: { is_admin: true },
});
```

- **빈 배열이 돌아오거나 오류가 나면 정상입니다.** 클라이언트가 자기 권한을
  올리지 못한다는 뜻입니다.
- **성공하면서 `is_admin: true`가 돌아오면 문제가 있습니다.** 2단계의
  `revoke`/`grant` 두 줄이 적용되지 않은 것이므로, `schema.sql`을 다시
  실행하세요. 이 상태에서는 로그인한 누구나 스스로를 관리자로 만들 수
  있습니다.

## 7. 잘 되는지 확인하기

```bash
npm run serve                  # 8123 포트로 정적 서버 실행
node tools/debug_auth.js       # 계정 흐름 전체 검증
```

`debug_auth.js`는 **모의 Supabase**를 상대로 돕니다. 따라서 프로젝트가
없어도 실행되고, AimonSite가 소유한 코드(PKCE 핸드셰이크, 세션 유지와 갱신,
원격 게시판, 거부된 쓰기 처리)를 전부 검사합니다. 반대로 말하면, **당신의
프로젝트에 정책이 제대로 걸렸는지는 검사하지 못합니다.** 그 부분이 6단계의
수동 확인입니다.

---

## 자주 겪는 오류와 해결

| 증상 | 원인과 해결 |
| --- | --- |
| Google 화면에서 `redirect_uri_mismatch` | 3-3에서 등록한 리디렉션 URI가 Supabase의 callback 주소와 정확히 일치하지 않습니다. 끝의 슬래시, `http`/`https`, 프로젝트 ref를 한 글자씩 대조하세요. |
| "이 앱은 차단되었습니다" / 접근 거부 | OAuth 동의 화면이 "테스트 중" 상태인데 본인 계정이 테스트 사용자에 없습니다 (3-2). |
| 로그인 후 사이트로 못 돌아오고 멈춤 | 4단계의 **Redirect URLs**에 현재 접속 중인 주소가 없습니다. 로컬이라면 포트까지 정확히 일치해야 합니다. |
| 로그인 버튼이 아예 안 보임 | `core/backend/config.js`의 두 값이 비어 있습니다. 저장 후 새로고침했는지 확인하세요. |
| 글쓰기가 "허용되지 않은 작업"으로 실패 | RLS 정책이 거부한 것입니다. 로그인이 실제로 되어 있는지, `schema.sql`이 전체 실행됐는지 확인하세요. |
| 관리자 답변이 거부됨 | 해당 계정의 `profiles.is_admin`이 아직 `false`입니다 (6단계). |
| 게시글이 하나도 안 보임 | 로그인하지 않은 상태에서는 공용 게시판을 읽을 수 없습니다. 로그아웃 상태에서는 이 브라우저의 로컬 게시판이 표시됩니다. |

## 로그인하면 달라지는 것, 달라지지 않는 것

**달라지는 것 — 두 가지뿐입니다.**

- 건의글이 "이 브라우저의 것"이 아니라 **당신의 것**이 됩니다. 이름으로
  등록되고, 어느 기기에서 로그인하든 같은 글과 답변을 볼 수 있습니다.
- 관리자 계정이라면 운영 화면이 **실제 권한을 가진 화면**이 됩니다.
  로컬 표시용 토글이 아니라 서버가 인정하는 역할입니다.
- (그리고 이것이 나중에 PvP가 사용할 신원입니다.)

**달라지지 않는 것.**

- 훈련 기록은 그대로 localStorage에, 이 기기에만 남습니다. 세션, 히스토리,
  설정 모두 로그인 여부와 무관합니다. 랜딩 페이지의 "기록은 기기를 떠나지
  않습니다"라는 문구는 계정이 조용히 뒤집는 기본값이 아니라 약속입니다.
- 백엔드를 설정하지 않은 빌드는 예전과 완전히 동일하게 동작합니다.
  로그인 버튼도, 네트워크 요청도 없습니다. 이 로컬 대체 경로는 임시방편이
  아니라 영구적인 설계입니다.
